# Adesh Binary ABI Specification (Version 1.0)

This document specifies the official **Adesh Binary Application Binary Interface (ABI v1)** governing object files, symbol resolution, calling conventions, scope-aware RAII drop tables, panic unwinding, and runtime contracts for the Adesh ecosystem.

---

## 1. Object Identification & Header (`.adesh.meta`)

Every object file generated by the Adesh toolchain contains an `.adesh.meta` section with the following 32-byte binary header:

```text
Offset (bytes)  Size (bytes)  Field                   Description
0x00            8             Magic                   0x7F 'A' 'D' 'E' 'S' 'H' 0x01 0x00
0x08            4             ABI Version             0x00000001 (v1.0)
0x0C            4             Compiler Hash           Build identifier hash
0x10            2             Target Arch ID          Architecture code (e.g. 1 = x86_64, 2 = aarch64)
0x12            2             Target OS ID            OS code (e.g. 1 = Linux, 2 = Windows, 3 = macOS)
0x14            1             Pointer Width           32 or 64 bits
0x15            1             Endianness              1 = Little-endian, 2 = Big-endian
0x16            2             Memory Model Flags      Bit 0 = 1 (Ownership & RAII, non-GC)
0x18            4             Feature Flags           Target CPU feature bits (e.g., AVX2, NEON)
0x1C            4             Reserved                Reserved for ABI v2 extensions
```

## 2. Symbol Mangling Standard

All exported and internal symbols in Adesh modules are encoded deterministically using the following schema:

```text
_A<pkg_len><pkg><mod1_len><mod1>...<item_len><item>E[<sig_hash>]
```

### Examples:
- Function `std::io::println`: `_A3std2io7printlnE`
- Function `std::collections::hash_map::insert` with signature hash: `_A3std11collections8hash_map6insertE12345678`

## 3. Scope-Aware Instruction-Range RAII & Unwind Model

Adesh **does not have a garbage collector**. Memory and resources are managed at compile time via **affine ownership, lifetimes, and RAII drops**.

### Correctness Rule:
The unwinder **never** executes a global list of drop functions blindly. Instead, the compiler and linker emit a `.adesh.unwind_map` section mapping instruction intervals to the precise active variables at each program counter:

```text
Function: foo()
  Instruction Range [0x00..0x10): Constructing A -> Cleanup State 0 (No drops)
  Instruction Range [0x10..0x30): 'A' is initialized -> Cleanup State 1:
      1. drop(A)
  Instruction Range [0x30..0x70): 'A' and 'B' are initialized -> Cleanup State 2:
      1. drop(B) (LIFO)
      2. drop(A)
  Instruction Range [0x70..0x80): Function Epilogue / Returned -> Cleanup State 0 (No drops)
```

### Table Layout (`.adesh.unwind_map`):
1. **Magic**: `b"AUNWND\x01\x00"`
2. **Function Descriptors**:
   - `Function Name` (length-prefixed UTF-8)
   - `Virtual Address` & `Size`
   - Array of `ScopeUnwindAction`:
     - `start_offset: u32`
     - `end_offset: u32`
     - `cleanup_state_id: u32`
     - `drop_targets: Vec<String>` (executed in exact LIFO order)

## 4. Target Maturity Classification

Adesh classifies all supported platforms into three distinct production readiness tiers:

### Tier 1 — Supported & Production Verified
*Continuous End-to-End Test Suite, Binary Execution Validation, Full Toolchain.*
- `x86_64-linux` (ELF64, GNU/Musl)
- `x86_64-windows` (PE32+, Windows x64 SEH Unwind)
- `aarch64-linux` (Linux ARM64, System V)
- `aarch64-macos` (Apple Silicon Mach-O 64)
- `x86_64-macos` (Intel macOS Mach-O 64)
- `wasm32-wasi` (WebAssembly Core 2.0 / WASI Preview 1)
- `i686-windows` (Windows PE32 x86)
- `i686-linux` (Linux ELF32 x86)

### Tier 2 — Experimental
*Codegen and Object Linking Validated; Ongoing Platform Hardware Run Validation.*
- `riscv64-linux` (RISC-V 64-bit LP64D ELF)
- `riscv32-none` (RISC-V Embedded Bare-Metal)
- `ppc64le-linux` (PowerPC 64-bit Little-Endian ELFv2)
- `armv7-linux-gnueabihf` (32-bit ARM Hard-Float)
- `nvptx64-cuda` (NVIDIA CUDA Fatbin)
- `amdgcn-rocm` (AMD ROCm HSACO)
- `qpu-quantum` (QIR / OpenQASM 3.0 Classical-Quantum Packages)

### Tier 3 — Declared
*Binary Format Header, Section Layout, and Relocation Table Specifications Defined.*
- `s390x-linux`, `mips64-linux`, `loong64-linux`, `sparc64-solaris`, `ppc64-aix` (XCOFF), `spirv-vulkan`, `hexagon-qdsp6`, `ane-apple`, `ethos-arm`, `tpu-google`.

## 5. Standard Calling Conventions

- **x86_64 Linux / macOS (System V AMD64 ABI)**:
  - Integer Arguments: `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`
  - Floating Point Arguments: `xmm0` – `xmm7`
  - Return Values: `rax`, `rdx` / `xmm0`, `xmm1`
  - Callee-Saved Registers: `rbx`, `rsp`, `rbp`, `r12`, `r13`, `r14`, `r15`
  - Stack Alignment: 16-byte aligned before `call`.

- **x86_64 Windows (Microsoft x64 ABI)**:
  - Integer Arguments: `rcx`, `rdx`, `r8`, `r9` (with 32-byte shadow space on stack)
  - Return Value: `rax`
  - Callee-Saved Registers: `rbx`, `rbp`, `rdi`, `rsi`, `r12`..`r15`, `xmm6`..`xmm15`.

- **AArch64 (ARM64)**:
  - Arguments: `x0` – `x7` / `v0` – `v7`
  - Return Value: `x0`, `x1`
  - Callee-Saved Registers: `x19` – `x28`, `x29` (FP), `x30` (LR), `d8` – `d15`.
